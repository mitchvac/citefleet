# Tilda

- **Market share:** 0.8% of all websites (W3Techs, 2026-09-11)
- **Category:** SaaS site builder
- **File access:** none. No filesystem, no file manager, no root-file upload, and no
  write API. The only way to get a real web root is to export the site and host it
  yourself (Business plan).
- **Automatable by the CiteFleet script (rclone):** no. Tilda's public API is
  **read-only** — every method is a GET that returns content; there is no endpoint
  that writes settings or uploads a file.
- **Docs consulted:** https://help.tilda.cc/search-engine (EN) /
  https://help-ru.tilda.cc/search-engine (RU, same article, fuller),
  https://help.tilda.cc/export / https://help-ru.tilda.cc/export,
  https://help-ru.tilda.cc/api,
  https://help-ru.tilda.cc/domain-confirm,

## Where the web root is

There isn't one, and Tilda is the most closed platform of the five. Tilda generates
`/robots.txt` and `/sitemap.xml` itself and offers no editor for either. There is no
mechanism of any kind — no upload, no template, no redirect to an external host —
for placing an arbitrary file at the root.

The single exception is **code export** (Business plan): Tilda hands the customer a
`.zip` of the whole site, which they upload to their own server via FTP. At that
point they have a genuine `public_html/` and every file in the origin pack is
trivial — but they are no longer hosted on Tilda.

## Steps to install the five files

### 1. `robots.txt` — **cannot be edited**

Tilda, verbatim (RU): «Оба файла генерируются Тильдой автоматически, ничего
дополнительно делать не нужно.» — *"Both files are generated automatically by Tilda;
there is no need to do anything else."* The English article says the same: "Both
files are generated automatically by Tilda; there is no need to do anything else."

There is no robots.txt field anywhere in Site Settings. The only settings that touch
the file at all are:

- **Настройки сайта → SEO → Дополнительно** (Site Settings → SEO → Additional): a
  checkbox «Использовать схему HTTPS в robots.txt, sitemap.xml и метатеге canonical
  URL» — *"Use the HTTPS scheme in robots.txt, sitemap.xml and the canonical URL meta
  tag."* It changes the scheme in the generated files, nothing else.
- **Настройки сайта → SEO**: a checkbox «Запретить поисковикам индексировать сайт»
  — *"Prevent search engines from indexing the site."* A site-wide off switch, and
  per-page there is **Настройки страницы → SEO → Отображение в поисковой выдаче →
  Настроить отображение в поисковой выдаче** with «Запретить поисковикам
  индексировать страницу».

No `Sitemap:` line can be added, no `User-agent` group, no `Allow`/`Disallow` rule.
Searched the whole Tilda SEO guide (the platform's only robots.txt documentation) —
every mention is descriptive, none is an editor.

### 2. `sitemap.xml` — cannot be edited or replaced

Same sentence covers it: auto-generated by Tilda, view it at
`http://mysite.com/sitemap.xml`. No editor, no upload, no exclusion list beyond the
per-page noindex checkbox.

And because robots.txt is not editable either, **there is no way to declare a
CiteFleet-hosted sitemap**. Both routes are closed, exactly as on Squarespace.

### 3. `llms.txt` — not possible

No llms.txt feature, and no general mechanism to serve an arbitrary root file.
Searched the Tilda help centre (EN and RU) for `llms`; nothing exists. Tilda's
"For Developers" section is Code Export, HTML embedding, the API, sending form data
to a server script, and a WordPress plugin — none of which serves a root file.

The obvious workaround, a redirect, is also closed. Tilda's 301 redirects live at
**Настройки сайта → SEO → Редиректы страниц (Code 301)**, and Tilda states two
disqualifying constraints:

- «Укажите старый и новый адреса страницы **без домена**, начиная со слэша» —
  *"Enter the old and new page addresses **without the domain**, starting with a
  slash."* The destination is a path, not a URL.
- «Переадресации работают **только в рамках одного домена**» — *"Redirects work
  **only within a single domain**."*

So `/llms.txt → https://citefleet.example/llms.txt` cannot be expressed. (The rule
that 301 redirects «работает только с несуществующих страниц» — *"works only from
non-existent pages"* — would not have been a problem; the domain restriction is.)

### 4. `.well-known/botcentral.txt` — not possible. Use DNS TXT.

No `.well-known` mechanism, no dot-directory, no file upload. Confirmed indirectly
by Tilda's own domain-verification article: for Google Search Console it documents
exactly two methods — «Мета-тег» (meta tag) and «DNS-запись» (DNS record) — and
conspicuously omits Google's third option, the HTML file at the site root. Tilda's
own verification UI (**Настройки сайта → Еще → Подтверждение прав**) accepts only
meta-tag values, for Yandex, Google and Facebook.

**Not a blocker.** Use the apex DNS TXT record; BotCentral scores it higher anyway.
Tilda's own instruction for the Google DNS method: go to the DNS control panel at
your **domain registrar** and add a TXT record with the copied value. Note that
DNS records are managed at the registrar (or in Tilda's DNS if the domain was bought
through Tilda Domains) — the Tilda site editor has no DNS UI of its own for a
third-party domain.

### 5. IndexNow key file — not possible

No root file, no `.well-known`, no external redirect, and no native IndexNow.
Searched the Tilda help centre for IndexNow — nothing. Tilda's search-engine
integrations are Google Search Console and Yandex.Webmaster registration
(**Настройки сайта → SEO → Google Search Console → Подключить**), which are
submission/verification tools, not IndexNow.

The `keyLocation` fallback is unavailable too: there is no writable path on the
site's own host at all.

## The `.well-known/` problem

Moot, in the strongest sense — nothing can be placed there and nothing needs to be.
Use the apex DNS TXT record for the BotCentral proof.

## Gotchas

- **Everything is auto-generated and untouchable.** Tilda is the only provider in
  this batch where *none* of the five files can be installed while the site remains
  on Tilda. Do not present Tilda as "partly supported" — it is not supported.
- **Redirects are same-domain only.** This kills the redirect-to-external-host trick
  that works on Shopify and Wix.
- **The API is read-only.** `getprojectslist`, `getprojectinfo`, `getpageslist`,
  `getpage`, `getpagefull`, `getpageexport`, `getpagefullexport` — all GET, all
  returning JSON, base `https://api.tildacdn.info`. There is no write method. It is
  Business-plan only, keys from **Настройки сайта → Экспорт → API**, and rate-limited
  to «150 запросов в час» (150 requests per hour) with an explicit warning that
  account blocking follows abuse.
- **Code export is Business-plan only** — «Данная опция доступна только на линейке
  тарифов Business, от 5 сайтов и больше» (*available only on the Business plan tier,
  from 5 sites upward*) — and comes with real strings attached: the Tilda-side HTTPS
  certificate stops working ("Free SSL certificate will be disabled for the exported
  project"), page passwords are not exported, and CRM / Membership / catalog /
  feeds control panels do not come along.
- **The export licence is restrictive.** Tilda forbids deploying the exported code on
  a domain other than the one named in Site Settings, forbids redistributing it, and
  states «Запрещено вносить изменения в программный код вне платформы Тильда» —
  *"It is forbidden to make changes to the program code outside the Tilda platform."*
  Adding new files such as `robots.txt` alongside the export is arguably not a
  modification of Tilda's code, but a customer should read the terms before CiteFleet
  tells them to edit an export. Flagging this as a legal question, not a technical one.
- **`.htaccess` is shipped as `htaccess`.** After export the customer must rename it.
  Tilda notes the file "only works under the Apache web server"; on Nginx they must
  write the rules themselves.

## If files cannot be placed

They cannot — not one of the five, while the site is hosted on Tilda. Two honest
answers to give a Tilda customer:

1. **Minimum viable:** apex DNS TXT record for the BotCentral proof. That is the only
   part of the origin pack achievable on a Tilda-hosted site, and it is achieved at
   the registrar, not in Tilda.
2. **Full pack:** export the site (Business plan, **Настройки сайта → Экспорт →
   «Скачать .zip архив» → «Начать экспорт»**), upload the unpacked folder to their
   own server over FTP, rename `htaccess` to `.htaccess`, and then drop all five
   files into the document root like any ordinary host — at which point rclone-based
   CiteFleet automation works normally. They lose Tilda-side SSL, page passwords, and
   the CRM/catalog/feeds panels in the process.

For CiteFleet's provider matrix, Tilda should be classed **"not possible — this host
cannot serve the pack"**, with the export path noted as the only escape.

## Automation

None on-platform. The Tilda API (Business plan, `https://api.tildacdn.info`) is
read-only content sync:

| Method | Purpose |
|---|---|
| `/v1/getprojectslist` | list projects |
| `/v1/getprojectinfo` | project info |
| `/v1/getpageslist` | list pages in a project |
| `/v1/getpage` | page info + body HTML |
| `/v1/getpagefull` | page info + full-page HTML |
| `/v1/getpageexport` | page info for export + body HTML |
| `/v1/getpagefullexport` | page info for export + full-page HTML |

All GET, all requiring `publickey` and `secretkey`, 150 requests/hour. Nothing here
writes site settings, robots.txt, sitemap.xml, redirects, or files. A CiteFleet
integration could at most *read* a Tilda site to build a sitemap or an `llms.txt` —
and would then have to host that output somewhere else, because Tilda will not serve
it.
